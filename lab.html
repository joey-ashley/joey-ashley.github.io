How I run the lab

One repository describes the whole site

The lab is a handful of Proxmox VE hosts, the guests running on them, the network between them, and the services that turn a pile of hardware into a site: DNS, time, a certificate authority, backups, and remote access. I don't configure any of it by hand. One Git repository describes the site, and tooling turns that description into the running thing.

The idea

There are two kinds of source in the repository. The first I call intent: what exists, meaning sites, network segments, address blocks, devices, hosts, and services. The second is policy: who is allowed to reach what, written as zones, a reachability matrix, and rule sets. The security page draws the matrix. Both are plain text files, validated against a schema, and deliberately written in no particular tool's vocabulary.

Generators read those files and write out what each tool wants, in the shape it wants: variables for OpenTofu, an inventory and group variables for Ansible, zone data for the DNS servers, a client map for SSH. That makes OpenTofu and Ansible adapters rather than sources of truth. If a root module or a role needs a fact, the fact gets added to intent and the generator passes it along. Nothing is hard-coded on the tool side.

How a change lands

  1. Make a branch and change whatever needs changing: intent, policy, or the adapter code.
  2. Run the generators, linters, and tests locally, then commit the generated files alongside the change that produced them.
  3. Open a pull request. CI runs the same checks I ran locally, plus a few more: formatting and lint for every language in the tree, schema validation, a check that every name follows the naming standard, a rebuild of all generated files (any difference fails the build), the test suite, and a plan of each OpenTofu root against a mocked provider.
  4. Merging is the approval to apply. The apply runs from a control node using the same task targets the pipeline uses, so there's no way to do something by hand that the pipeline couldn't do again.

Rules I don't break

  • State never goes into Git. It lives in an object store, encrypted before it leaves the control node, and there's a second encrypted copy somewhere else.
  • Secrets only exist as files encrypted with SOPS and age, to hardware keys. Anything that looks like a credential anywhere else fails the secrets check.
  • I never hand-edit a generated file. The build regenerates everything and fails if anything differs.
  • Every name gets checked against a written naming standard before it can exist.
  • Commits are signed, and main only takes pull requests with passing checks.
  • Any decision that will matter past the day I made it gets written up as a dated record: the context, the options I considered, what I chose, and what that costs. Reversing one means writing a new record and shipping it in the same pull request as the code change.

Why I do it this way

Partly because it's good practice. Mostly because the household actually depends on this stuff, and I'm the only one running it. If I did it by hand I'd be relying on memory, and memory is what fails late at night when DNS is down. This way the repository says what the site is supposed to be, the pipeline checks that it's true, and rebuilding from scratch is a documented procedure instead of a weekend of guessing. When something breaks, I don't have to wonder what I changed. It's in the Git log.

The repository is private, but I'm happy to share a read-only copy if you ask.
