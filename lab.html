How I run the lab

One repository, treated as a compiler

The lab is a few Proxmox VE hosts, the guests on them, the network between them, and the services that make a site out of it: name resolution, time, a certificate authority, backups, remote access. None of it is configured by hand. A single Git repository holds a description of the site, and tooling turns that description into the running thing.

The idea

The repository has two kinds of source. Intent says what exists: sites, network segments, address blocks, devices, hosts, services. Policy says who may reach what: zones, a reachability matrix, rule sets. Both are plain files, checked against a schema, and written in no tool's vocabulary.

Generators read those files and write the inputs of each tool in that tool's own shape: variables for OpenTofu, an inventory and group variables for Ansible, zone data for the DNS servers, a client map for SSH. OpenTofu and Ansible are adapters. A root or a role never carries a fact of its own; if it needs one, the fact goes into intent and the generator hands it over.

How a change lands

  1. Branch, and change intent, policy, or adapter code.
  2. Run the generators, the linters, and the tests locally. Commit the generated files with the change that caused them.
  3. Open a pull request. CI runs the same gates: formatting and lint for every language in the tree, a schema check, a name lint against a naming standard, a rebuild of every generated file that fails on any difference, the test suite, and a plan of each OpenTofu root against a mocked provider.
  4. Merge is approval to apply. The apply runs from a control node through the same task targets the pipeline uses, so nothing is possible by hand that the pipeline cannot repeat.

Rules that do not bend

  • State never enters Git. It lives in an object store, encrypted before it leaves the control node, with a second encrypted copy elsewhere.
  • Secrets exist only as files encrypted with SOPS and age, to hardware keys. A credential-looking string anywhere else fails the secrets gate.
  • A generated file is never edited by hand. The build regenerates it and fails on a difference.
  • Every name passes a lint against a written naming standard before it exists.
  • Commits are signed, and the main branch accepts only pull requests with passing checks.
  • A decision that outlives the day it was made becomes a dated record, with the context, the options, the decision, and its consequences. Reversing one means a new record and the code change in the same pull request.

Why it is built this way

A home lab is a place to practice the craft under a real constraint: the household depends on the result, and there is one person to run it. The method above is what makes that tractable. The tree says what the site is, the pipeline proves the tree, and a rebuild from nothing is a documented path rather than a memory. When the site breaks, the question is never "what did I change", because the answer is always in Git.

The repository is private. A read-only copy is available on request.
