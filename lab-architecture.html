Architecture

What the running thing actually is

The lab page is about how a change flows. This one is about what it flows into. The short version: one gateway, a small switched core, three always-on nodes that form a cluster, two more that deliberately don't, and a few dozen guests sorted by what they're for.

The hardware, and why it's shaped like that

The gateway owns all inter-segment policy and hands out addresses. Below it, two aggregation switches are the core, with a rack distribution switch hung off both of them and the access points off that. Every node bonds across two switches, so a switch can die without a node noticing much.

There are three kinds of compute, and the split is on purpose:

  • The cluster is three small, identical nodes, each with local ZFS. There's no shared storage and no Ceph: guests replicate between nodes on a schedule instead. The important guests get an HA resource, a rule for which node is home, and replication every five minutes to every other member. The rest replicate every fifteen minutes to the next node along. Any guest the family can't live without runs here, because this is the part that never sleeps.
  • The lab node stands alone and holds the lab plane, a container-based network lab with its own routing domain. Nothing in the lab domain is routed anywhere in the site, so a lab can't reach the house no matter how badly I misconfigure it.
  • The lifeboat node also stands alone, and carries the backup server and the second monitor. That's deliberate: if the cluster is the thing that fails, I want the thing that watches it and the thing that restores it to be somewhere else. Each failure domain gets a watcher outside it.

Two of everything the family or the platform can't live without: two resolvers, two authoritative name servers, two time sources, two subnet routers. One of everything else, with a tested restore.

Sixteen segments, seven zones

The network is sixteen VLANs. The subnet of each one has the VLAN number baked into it, so an address tells you which segment it's on without looking anything up, and the IPv6 side uses the same number as its subnet ID. Two of the VLANs, the cluster heartbeat and the storage network, are layer 2 only with no routed path at all. The rest are grouped into the zones the security page describes.

Guests get static addresses from intent, applied by cloud-init at first boot. The only DHCP pools are on the segments where people and devices live.

The guests, by plane

Each guest in intent has a role, a tier, a placement, and a list of the services it offers with their ports. The firewall of each guest is generated from that list with a default of drop, so a port that isn't declared isn't reachable, even from inside its own zone. On the cluster they sort into planes:

  • Names: a pair of recursive resolvers and a pair of authoritative servers.
  • Time: two time servers, handed out by DHCP.
  • Trust: the certificate authority, an issuing intermediate whose root stays offline.
  • Truth: the source of truth for addresses and devices, and the asset register beside it.
  • The household: the home page and the home automation hub, the two things the family actually touches.
  • Remote access: the pair of subnet routers for the tailnet, and the tunnel client in the DMZ.
  • Operations: a control node that lives on the site, and two CI runners, all on a segment of their own that only the admin networks can reach.

The layer below DNS doesn't need DNS. The nodes pin each other in their hosts files from a generated list, so the cluster comes up and talks to itself before a single resolver exists.

Where state lives

The infrastructure code is four OpenTofu roots: one that owns the state bucket itself, one that owns the GitHub repository and its branch rules, one that builds guests, and one that builds the cluster's HA resources, replication, and backup jobs. The guest and platform roots run once per placement, meaning once per Proxmox API, with a state object of their own each time, so a run for one placement can never read or write another's.

Every state object lives in an object store, locked on every plan and apply, and encrypted on the control node before it leaves. No state file is ever in Git. After every apply I pull a second copy and encrypt it to the two hardware keys as a dated file somewhere else. The roots never read each other's state. The only way facts move between them is through the variables the generators write, which keeps the dependency graph visible in the tree instead of hidden in a remote-state lookup.

A control node is any machine that can plan, apply, decrypt, and run the plays: the laptop, the workstation, and one guest on the site. The tree pins every tool a control node runs, down to the version, and a check target prints one line per requirement with the runbook section that fixes it. Targets that should only ever run from a laptop, like a state backup or the CA play, refuse to run on the guest.

DNS

Every name in the site is compiled from intent. The generator writes three zones per site: the forward zone, the IPv4 reverse zone, and the IPv6 reverse zone, with a PTR for every address record, so forward and reverse never disagree. A host is published only once it carries a tag saying it's live. Until then it has a name and an address in intent and no record anywhere, which is how a planned guest can be fully described without lying to the resolvers about whether it exists.

Service aliases follow a few rules: an alias with one target is a CNAME, an alias with two is a round-robin pair of A records, and a VIP is an A record on the shared address with a short TTL. A pair's alias is published only when both members are. The generated zones are pushed with octoDNS into the primary authoritative server, and the secondary follows by zone transfer.

The resolvers stub those zones to the authoritative pair, and they do one more thing: they answer the handful of public names with the internal address of the guest that serves them. From inside the house you reach a public application directly. From outside you reach it through the tunnel. The public zone is compiled the same way from its own small intent file, holds only the records I've declared, and refuses to delete anything unless told to in so many words.

Decisions are records

Any decision that will matter past the day I made it becomes one file in the repository, in a fixed shape: a status line, then four sections, Context, Options considered, Decision, and Consequences. The file name is the title. A test holds the shape, so a record missing a section fails CI like anything else.

The rules around them matter more than the shape:

  • A record is never edited into saying something different. It can grow by a dated addition that reverses nothing and changes no word that stood before, and it can be corrected on the day it merged with its status line saying so. That's it.
  • Reversing a decision means writing a new record that names the one it replaces, setting the old one to "superseded by" the new file, and making the code change in the same pull request. The reasoning and the change land together, or not at all.
  • Records chain. One question in the lab, how the nodes' uplinks are cabled, has six records, each one replacing a single item of the one before and carrying the rest forward. Reading the chain is reading how my understanding changed, in order, with dates.

The practical effect is that the repository answers "why is it like this?" as reliably as it answers "what is it?". When I come back to something six months later, the options I didn't take are still written down next to the one I did.
