How I run it Security

Security

Ten zones, one matrix, and nothing open on the WAN

The lab page says that policy is "who is allowed to reach what", written as zones, a reachability matrix, and rule sets. This page is what that looks like. The gateway is the only firewall between segments. The switches don't filter, and each guest has a host firewall of its own on top. Every rule the gateway holds comes from three plain text files in the repository, and the files are checked against a schema like everything else.

Zones are trust levels, not VLANs

The first version of the design had a zone for every VLAN: twelve custom zones plus the built-in ones, which works out to 182 ordered pairs in the matrix, each one set by hand. I threw that out and grouped the sixteen VLANs by how much I trust what's on them. Five custom zones came out of it:

  • infra, the management plane: the network gear, the hypervisor nodes, the backup servers, the out-of-band controllers and the PDU, the control node, and the CI runners.
  • services: every platform service, and the security plane alongside it.
  • people: the family's devices and the admin laptop.
  • things: smart home gear, printers, cameras, and the TVs.
  • isolated: the cluster heartbeat VLAN, the storage VLAN, and quarantine. Reaches nothing, reached by nothing. These exist as zones at all only because the controller can't create a network without a gateway interface, so the zone is what takes the route away.

The built-in zones keep their jobs. DMZ holds the one host that talks to the public. Hotspot holds guests and the employer-issued laptops, with no captive portal, and clients in it can't see each other. VPN is the break-glass WireGuard path. External is the WAN. The built-in Internal zone, where the controller's default between networks is allow-all, is kept empty on purpose, so a new network can't land somewhere permissive by accident.

When two networks in one zone need different treatment, that's a policy scoped to the network inside the zone pair, never a new zone. The cameras are fenced inside things that way: no internet, no resolver, and only the recorder pulls from them. The security segment is fenced inside services the same way.

The matrix

Every ordered pair of zones is blocked unless a row in the matrix opens it, and every pair ends in the controller's own built-in block rather than one of mine. That last detail matters: the controller places a derived return-traffic policy below every user policy, so a user-written block at the end of a pair would shadow the return traffic of the reverse pair's allows. Learned the hard way, now written down.

Most of the open circles are small. things may reach services for DNS and time, and for the home automation hub, and that's all. The DMZ may reach the three published targets on one port each, plus DNS and time. The hotspot zone may reach exactly one thing inside the house: the printer. The management plane may reach the services on the ports a deploy needs, from the control node and the runners by name, and the runners get a narrower set still, because they check the site and never apply to it.

A row in the matrix doesn't list ports. It names rule sets, joined with a plus sign, and the rule sets live in their own file. A rule set is a short list of protocol, ports, and optionally which hosts it applies to, by the host's name in intent. So dns-ntp means "53 and 853 to the two resolvers, 123 to the two time servers", and it means that in every row that uses it. When a resolver's address changes, nothing in policy changes.

Egress is a policy too

The site resolvers are the only way out for DNS. Every other zone that may reach the internet gets an egress rule set with a block for DNS, DNS over TLS, and SMTP above it, so a device can't quietly use a public resolver or send mail on its own. The cameras get no egress at all. The things zone gets the web and nothing else.

The way in

No port on the home WAN is open. There are three paths, each for a different purpose, and they're kept apart on purpose:

  1. Admin access comes in over the tailnet. A pair of subnet routers on the services segment advertises the site's routed segments and nothing else. They rewrite the source address, so every connection from the tailnet arrives at a node or a guest looking like one of the two routers. The site admits the routers by their role, never by a tailnet address. Who may use that path is decided in the tailnet's access rules, by identity, not by which network someone is sitting on.
  2. Public applications go out, not in. The one host in the DMZ is a tunnel client that connects outward to a small VPS. The VPS terminates TLS for the handful of public names and forwards them down the tunnel to one address and one port each. Inside the site, the resolvers answer those same public names with the internal address, so a person at home never leaves the house to reach them.
  3. WireGuard on the gateway is break-glass. It exists for the day the tailnet is unreachable, it's an everyday path for nothing, and it gets tried once a quarter so I know it still works.

Keys, secrets, and certificates

  • Secrets exist only as files encrypted with SOPS and age, and the recipients are two hardware keys: the one on my keyring and the one in the desk drawer. Decrypting takes a PIN and a touch. A string that looks like a credential anywhere else in the tree fails CI.
  • Every internal host gets its certificate from the site's own step-ca. The issuing intermediate runs as a guest; the root key stays offline under the same two hardware keys. Internal names never appear in the public zone.
  • The CI runners hold no secret. They check the site over SSH and plan each infrastructure root against the real APIs, and they go back to a clean snapshot every night. They can't apply anything. Applying is a person, from a control node, after a merge.
  • Commits are signed, and the main branch takes nothing but a pull request with passing checks.

What's honestly still interim

A design document that says everything is finished is lying. The matrix file carries a note on every row that isn't yet what the design says. Several pairs inside the management plane are still "allow all, with logging" while I watch a week of real flows before narrowing them, and two of the egress blocks are written down as owed rather than done. A separate plan tracks the difference between what the policy files say and what the controller holds today, and that difference is what the next pull requests close.

The design itself is a dated decision record in the repository: the context, the options I considered (one zone per VLAN, one zone per trust tier, or fewer still), what I chose, and what it cost. The record is why the matrix has 90 pairs instead of 182.
