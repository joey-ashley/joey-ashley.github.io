Rebuilding from nothing

Nine stages, and what proves each one is done

The lab page claims that rebuilding from scratch is a documented procedure. This is the shape of that procedure. The real runbooks are in the private repository and are long, with the exact commands, the order of the reboots, and the things that bit me. What's here is the structure: what each stage needs, what it produces, and how I know it's finished before the next one starts.

What has to survive

A rebuild starts from five things that live outside the site, and the whole method depends on keeping it to five:

  • The Git repository, hosted off-site.
  • The state of each infrastructure root, in an object store, encrypted. Plus the dated second copies.
  • Two hardware keys. Every secret in the tree is encrypted to both. Either one is enough.
  • A password manager, holding the object store's token, the keys' PINs, and nothing the tree could hold instead.
  • A laptop, which becomes the first control node.

The path never depends on the guests it's about to build, and it never depends on the cluster to rebuild the cluster. While the cluster is down, the laptop resolves names through the resolver on the standalone lifeboat node, or through the gateway if that's gone too. That's the reason the lifeboat node exists.

The stages

  1. A control node. Clone the repository. One script installs the toolchain the tree pins, down to the version of every tool, and prints no secret while it does it. Then the hardware key's identity file, an environment file with the object store credentials, SSH keys, and Git set up to sign. A check target prints one line per requirement, ok or missing, with the section of the runbook that fixes it. The stage ends when every line is ok.
  2. Secrets open. Prove the round trip: decrypt the one secrets file with a PIN and a touch. The proof checks the length of a value, never prints it. If this fails, nothing after it can run, so it's second and not sixth.
  3. The network. Port profiles on the switches before anything is cabled, so a node comes up on the right VLANs the first time. The gateway gets its zones and its matrix. The proof is a plain one: a cable into the gateway's untagged network always works, because that's the network every uplink carries.
  4. The nodes. The hypervisor goes on at the console from a script with named phases: a preflight that lists every drive by its stable path, a phase that builds the storage pool and refuses to touch the boot pool, a network phase that writes the bridges and bonds, and a verify phase. Between them a play from the control node sets the repositories, does the one full upgrade, and writes the hosts file so the nodes can find each other before DNS exists.
  5. The cluster. One node founds it and the others join, each with its node ID fixed in the command, so the order of the joins can't change the result. A node that joins must hold no guest. The proof is three of three in quorum with two heartbeat links on every node.
  6. The roots. A role and one API token per control node, into the environment file and never the tree. Then the guests root for each placement: it fetches the cloud image pinned by hash, builds a template on each node, and makes one guest per host in intent with a firewall generated from its declared services. Then the platform root, which adds the HA resources, the replication jobs, and the backup jobs. Guests first, because an HA resource needs its guest to exist. Every root is done the same way: plan, apply, plan, and the second plan says no changes. A plan that would destroy or replace anything is a stop, not a warning.
  7. The plays. The site play runs the services in dependency order: the authoritative name servers and the resolvers, the time servers, the certificate authority, the subnet routers and the tunnel client, then the backup server, the source of truth, the register, the home page, home automation, the second monitor, the mail relay, the guest control node, and the runners. Until the authority exists, a guest signs its own certificate; that's a dated decision record, with an end condition. Each service has a live proof script that runs against the real guest with a timeout on every call.
  8. The zones. Generate the three zones from intent, plan the push, read the plan, apply. A change that touches the authoritative servers themselves goes one server at a time, secondary first, with the DNS proof after each. The proof is every published name resolving forward and reverse on all four name servers exactly as the generated zones say.
  9. The drills. A cluster that's never been broken on purpose isn't finished. Three checks, each timed and written down: a live migration over the storage network, each node restarted in turn with the guests following their home rules back, and one node's power pulled without warning. The last one is the one that matters.

After every apply of a root, a second copy of its state goes out, pulled from the bucket and encrypted to the hardware keys as a dated file. The target refuses to run on the guest control node, because a copy that lives on the site isn't a copy.

What makes the runbooks trustworthy

  • Every command is a task target. A runbook never says "run this binary with these flags". It names a target, and a person and CI call the same targets. There's one entry point, and a step that isn't in it doesn't exist.
  • The proofs are scripts, not tests. A live proof reaches the real site, puts a timeout on every remote call, and exits non-zero on a miss. CI never runs them. But the logic that judges the result is pure and has unit tests on fabricated facts, so no guest being down and no edit to intent can turn the test suite red.
  • The manual steps are listed, numbered, and honest. Each runbook opens with the things the repository cannot do: the console, the BIOS, the first key on a node, the token in the password manager. Each one gates the steps after it. Pretending they're automated would be the worst kind of lie, because it's the one you discover during the rebuild.
  • A technology new to the site gets a runbook and a guide before its milestone closes. The runbook says how to operate it. The guide says how it works and why it was chosen. The decision record says what else I considered.
  • The runbooks are read against the tree. Where a runbook names a pin, a port, or a path, a test checks that it matches what the role actually has. A runbook that drifts from the code fails CI.

I've done this path for real, not as a drill: the cluster was rebuilt from three empty machines while the services it would carry ran on the lifeboat node, and then taken over one guest at a time. The runbook for that is the longest file in the tree, and every step in it was either run or struck out with a date.
